# Public benchmark foundation — incomplete, not production-ready

This module contains reproducible manifest selection, transparent matching, metrics, a sequential local batch runner, an admin-only result import and review interface, consented usability records, and an exportable preliminary report. It is incomplete and not production-ready. A local, ignored PlantVillage sample has been downloaded as described below; no assessment results, participants or expert reviews are included. A separate Neon migration is provided but has not been applied. The existing farmer expert-review workflow is separate from this module.

## Audit and integration

The browser uses `/api/analyze`, which runs PlantNet then the existing OpenAI assessment (`server/index.js`) and may cache results and write diagnosis audit records. `createLocalAssessmentAdapter` calls this exact HTTP endpoint, not a substitute model. It does **not** reproduce the browser's image resizing, image-quality preflight, or farmer-selected category; record those differences and do not interpret a benchmark as a full end-to-end user experience. The response does not reliably expose token use; missing usage and cost remain null. Do not run against production: even with image retention disabled the endpoint writes assessment text to its configured audit backend. A local hostname alone does not prove the server uses isolated database credentials. Set up an isolated process with dummy secrets and an isolated local audit directory/database, verify configuration, and explicitly approve provider expenditure before making any real calls. The adapter does not create auth sessions or bypass the app's rate/quota controls. The local injected store interface is not a security boundary. Imported records use separate database tables and server-side admin authorization; these have not been integration-tested. Import requires provenance and rights-clearance assertions, which are not independent proof of either. Batch deduplication relies on the store implementing atomic uniqueness; the sample runner is sequential, does not retry automatically, and is not a durable job queue. Failure records must be deliberately versioned for a retry. Cancellation is best effort and a provider request already in flight may incur charges.

## Sources and rights review (31 October 2026)

* [PlantVillage repository](https://github.com/spMohanty/PlantVillage-Dataset) has raw/color, grayscale and segmented variants; the authors' [dataset card](https://huggingface.co/datasets/mohanty/PlantVillage) declares CC BY-SA 3.0 and 38 labels (see [source card](https://raw.githubusercontent.com/spMohanty/PlantVillage-Dataset/master/README_HF.md)). Attribute Mohanty, Hughes and Salathé, *Using Deep Learning for Image-Based Plant Disease Detection* (2016), DOI 10.3389/fpls.2016.01419. Confirm rights for the particular release and use, including derivative/share-alike obligations before redistribution.
* [PlantDoc repository](https://github.com/pratikkayal/PlantDoc-Dataset) contains train/test class folders and declares CC BY 4.0; its authors describe internet-scraped images. Attribute Singh et al., *PlantDoc: A Dataset for Visual Plant Disease Detection* (2020), DOI 10.1145/3371158.3371196. A repository licence is not conclusive proof that every scraped image has transferable rights. Confirm each image's provenance and reuse rights before ingestion; do not redistribute unverified images.

The local PlantVillage sample has been checked for exact duplicates and basic image decoding; near duplicates, class compatibility and cross-dataset overlap remain unverified. Exact checksum deduplication is supported on supplied candidates; it is not a near-duplicate check. The initial set currently contains **60 PlantVillage images**: 20 healthy and 40 diseased. The PlantDoc sample now contains 30 images; the difficult-case target remains unfilled. The manifest records the sampled release commit. To prepare it, independently verify images and label mappings, compute SHA-256 on original bytes, record the exact release commit, assign mutually exclusive categories and mark rights/image verification explicitly; then call `prepareManifest` with a fixed integer seed. Its selection reports rejected records and category shortfalls. Validate image decoding and perceptual overlap outside the manifest function. Do not set `supported` true until crop/condition mapping is independently approved. Original labels remain intact. Healthy and difficult assignments must be reviewed; the selector does not infer clinical status from label text.

## Scoring

`calculateMetrics` reports numerators, denominators and exclusions; unsupported, abstained and failed cases remain visible. Synonyms must be independently approved. Raw model confidence is an uncalibrated model output. Source-specific results should be reported separately, alongside coverage; these convenience functions do not yet provide per-crop grouping or reporting charts. Dataset labels are not expert verification. Public dataset agreement is not field-validated Malaysian diagnostic accuracy.

## Release blockers

Verify protected dataset-image storage and display in the target deployment, reviewer-specific permissions and qualification checks, immutable run metadata, product response attestation, charts, consent management, robust append-only auditing, server-side job locking, durable cancellation, quotas, server-enforced cost approval, retries and comprehensive tests. The current interface uses the admin allowlist for all benchmark review operations; an admin is not automatically an agricultural expert. Test all with isolated credentials and dummy users. Resolve the existing cross-user upsert risk before deployment. Review actual data rights, run image integrity and overlap checks, and secure approvals for provider costs. Do not deploy or describe the module as production ready until these controls and end-to-end checks pass.

## Local runner

`run-local.js` accepts a prepared JSON manifest with `selected` entries and a `localPath` relative to a local image root. The path and bytes are verified against that root and the SHA-256 manifest. First run without approval to print the operator-supplied estimate (in a consistent currency); adding `--approve-cost` makes actual network requests to `127.0.0.1:3002`. Stop with Ctrl-C. Result files are created exclusively in a separate directory with restrictive modes and no delete or overwrite function. This is a local single-process tool, not an authenticated multi-user service; filesystem permissions, backups and race-proof durable coordination still require production design. Never place results in a public directory or commit images. Do not run unless the local API process has been independently verified to use isolated data stores, test credentials and an approved provider budget. The command is:

```
node server/evaluation/run-local.js manifest.json /path/to/images /path/to/private-results workflow-v1 0.05
# After reviewing the estimate and isolating the server, repeat with --approve-cost.
```

The numeric rate above is an example input, not a provider price. The adapter currently labels JPEG/PNG by signature; signature checks do not establish that an image can be safely decoded. Its result records retain the source manifest fields available to it, model/policy metadata where present, elapsed time and raw response without the feedback capability token. Version identifiers are supplied by the operator and must capture the source revision, prompts and model configuration. Cached responses are flagged; exclude or separately analyse their timing. `costApproved` expresses operator approval in this local tool only; it is not a substitute for server-side authorization or budget controls.

## Migration and rollback plan

`neon/migrations/0002_evaluation.sql` creates separate case, review and usability tables. It has not been applied. Review the schema, grants, role ownership and retention policy; take a recoverable backup and test it on an isolated Neon branch using the project's migration process. Verify that only the trusted server role can access the tables and that authenticated non-admin and anonymous requests are rejected. The migration revokes PUBLIC access but does not change the owner or any existing explicit role grants; check actual effective privileges. Do not grant browser roles access. Deploy only with explicit approval.

Rollback is destructive to benchmark data and is not automatic: export and verify any records and obtain explicit authorization, then on the isolated branch drop `evaluation_product_reviews`, `evaluation_product_scenarios`, `evaluation_reviews`, `evaluation_usability_sessions`, and finally `evaluation_cases` in dependency order. Never run a rollback against production without a separately approved recovery plan.

## Current limitations

The dashboard imports a local JSON result, shows metadata and review history, runs controlled product scenarios through the existing product search, records separate product verdicts, displays per-crop counts and exports a Markdown summary. It can serve checksum-verified local dataset images to authorized admins when an evaluation image root is configured, but does not perform batch execution, offer expert-only accounts separate from admins, produce charts, or analyse usability feedback. Product scenarios are administrator-supplied records and must be independently corroborated before being used as evidence. No clinical, financial or field-effectiveness claim follows from it. Imports are trusted administrator assertions and can contain erroneous labels, metadata or measurements. Agreement is recalculated using exact labels; the dashboard does not yet manage or apply approved synonyms. The overview can combine multiple workflow versions and is labelled accordingly; use separately controlled runs before making comparisons. Access, migration, UI and end-to-end behavior have not been tested against a database.

The original image paths, original labels, tentative normalized labels, source, checksum, category, revision, licence notice and local filenames are retained per image. All archive CRC checks and macOS image decode checks passed; no identical SHA-256 image pairs were found. This is not a perceptual or cross-dataset duplicate check. Selection was random within the healthy and diseased portions of the published test split, not stratified by crop.

The images and manifest are in the git-ignored local dataset directory and are not imported into the database or served by the dashboard. Existing manifest output is replaced if the script is run again, so preserve reviewed manifests before rerunning.

## Latest implementation and release checks

Product scenario entry calls the existing `/api/products/search` endpoint, then saves the scenario and response separately; an administrator can record product review criteria. Product and assessment reviews are separate from the original outputs. Product matches are not proof of suitability. The scenario response is supplied by the administrator's browser and is not cryptographically attested: do not treat it as independently verified evidence. The existing admin allowlist protects the evaluation endpoints, but reviewer expertise is not verified by account membership. Product searches may consume application quota and contact the configured catalogue; none were run for this change.

The local runner creates an exclusive per-image/version lock before making a request. Locks persist after completion or interruption; a lock without a result needs manual investigation before any retry because the provider may already have charged. This is local filesystem protection, not distributed job locking. The runner uses the same shared decision policy as the app for uncertainty and treats HTTP 202 as incomplete. Browser-side capture quality and resize steps still differ. Per-crop metrics retain numerator and denominator and can be misleading for small or uneven samples. No independent benchmark result is currently available.

Before release: validate dataset rights and expert-approved mappings; provision isolated image storage and verify access control; test server authorization with dummy non-admins and reviewers; verify DB grants, migrations, backup and rollback on an isolated branch; implement server-side provenance of product responses and distributed execution/cost controls; test no cross-user disclosure, uploads, cancellation and retry; verify actual provider model/cost metadata; run the complete automated suite and browser accessibility checks; and obtain explicit deployment approval. None of the migrations have been applied.

Verification on 31 October 2026 used a disposable source copy, network-disabled sandbox and an empty environment. The evaluation module tests passed (16/16); evaluation dashboard and existing admin page tests passed (5/5). The broader suite reported 404 passed and one existing AssistantWidget error-path test failed despite rendering the expected error and contact links; its cause remains unresolved. A frontend build succeeded in the disposable copy, with a warning because the sandbox could not read Git metadata. Live providers, database migrations and the authenticated end-to-end flow were not tested.

## Local prototype image display

For a separately configured isolated prototype, set the server-only `EVALUATION_IMAGE_DIR` to the absolute `server/dataset/public-evaluation` directory. The admin-authenticated image endpoint looks only for checksum-named JPEG or PNG files in the `plantvillage` or `plantdoc` subdirectory, limits file size, verifies SHA-256, and disables caching. It requires a previously imported case with `rightsCleared: true` and does not clear rights itself. The current manifests keep that flag false. Do not expose this directory through static hosting. This code has not been exercised against a running database or browser.
